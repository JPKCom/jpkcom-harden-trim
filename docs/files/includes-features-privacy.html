features-privacy.php

Privacy features

Author enumeration, REST users, oEmbed author, users sitemap, Browse Happy, dashboard events, local avatars, commenter IPs, embed privacy, remote editor content and the core AI client. All of them are global: they protect anonymous visitors or act on data and requests where no user context exists, so the exempt roles do not apply. Every hook name and priority below was checked against the WordPress 7.1.3 source.

jpkcom_harden_trim_activitypub_answers_author()

features-privacy.php : 249

Whether the ActivityPub plugin itself answers this `?author=N` request.

jpkcom_harden_trim_activitypub_answers_author(array<string, mixed> $query, string $requested_url) : bool

ActivityPub (wordpress.org slug activitypub, read against 9.3.1) answers ?author=N with the actor document only when all of these hold, each decided by its own public API, never by a header test of ours:

  • \Activitypub\is_activitypub_request() (functions-request.php:70): ?activitypub, or an Accept header whose highest-quality type is activity+json or ld+json with the ActivityStreams profile (q-aware, q=0 refuses), plus its filter. Otherwise it does not suppress core's canonical redirect (class-router.php:301).
  • \Activitypub\should_negotiate_content() (functions-request.php:79): otherwise it renders the theme template (class-router.php:92).
  • author is the only argument in the query of the requested URL as core builds it from the Host header and REQUEST_URI (see jpkcom_harden_trim_author_is_only_query_arg()); otherwise core's redirect goes through.
  • \Activitypub\user_can_activitypub( N ) (functions-user.php:90): a user who is no actor gets no transformer (transformer/class-factory.php:109) and the theme renders the author archive.
  • The request reaches template_include, where ActivityPub renders its document (class-router.php:24). Core's template loader answers robots, favicon, feeds and trackbacks before that filter (template-loader.php:40-62), and sitemaps exit on template_redirect; a feed path such as /feed/?author=N keeps the raw query at author alone, yet core serves the author's feed (display name, by default the login). Any of their query vars (feed, tb, robots, favicon, sitemap, sitemap-stylesheet), from path, query or POST body, refuses.

The functions are looked up at call time. If any of them is missing (ActivityPub not loaded, or a version with a different API), the answer is false: an unknown ActivityPub is not trusted to answer.

Parameters
$query : array<string, mixed>

Parsed request query vars.

$requested_url : string

The requested URL as core builds it (jpkcom_harden_trim_requested_url()).

Tags
since
1.0.0
Return values
bool —

True when ActivityPub answers the request with its own document.

jpkcom_harden_trim_is_users_route()

features-privacy.php : 446

Whether a REST route is the users collection or anything below it.

jpkcom_harden_trim_is_users_route(string $route) : bool

Case-insensitive like core's route matching; a trailing slash is tolerated.

The anchor must keep core's semantics: WP_REST_Server::match_request_to_handler() (7.1.3 class-wp-rest-server.php:1172) matches with '@^' . $route . '$@i', no D modifier, so its $ also matches before a trailing "\n", and rest_api_loaded() only strips slashes (untrailingslashit()). Core therefore serves ?rest_route=/wp/v2/users%0A as the user list. Do not "tighten" this to \z: that would let exactly that request through.

REST route, e.g. /wp/v2/users/1.

jpkcom_harden_trim_anonymize_ip()

features-privacy.php : 675

Anonymise an IP address: IPv4 to /24, IPv6 to /48.

jpkcom_harden_trim_anonymize_ip(string $ip) : string

An IPv4-mapped IPv6 address (::ffff:a.b.c.d, as dual-stack listeners report IPv4 clients) is anonymised as the IPv4 address it carries; keeping its first 48 bits would store :: for every such client. Core's sanitiser keeps commas and spaces (comment.php:2424), so a proxy list anonymises its first valid address.

jpkcom_harden_trim_filter_comment_flood()

features-privacy.php : 761

`wp_is_comment_flood` callback: flood check against the anonymised IP.

jpkcom_harden_trim_filter_comment_flood(mixed $is_flood[, mixed $ip = '' ][, mixed $email = '' ][, mixed $date = '' ][, mixed $avoid_die = false ]) : mixed

wp_check_comment_flood() (7.1.3 comment.php:909) looks for a recent comment with comment_author_IP = <live IP> or the same e-mail address. While comment_ip is on, stored rows hold the shortened address, so for guests only the e-mail clause would still match and a guest changing the e-mail address on every comment was never throttled. This runs the same core check once more with the shortened form, so the IP clause works again, per /24 (IPv4) or /48 (IPv6) network.

Skipped when core already found a flood, for logged-in users (core checks the user ID), when the IP is already in its stored form, and when the site removed core's flood check.

$is_flood : mixed

Flood verdict so far.

$ip : mixed = ''

Live commenter IP.

$email : mixed = ''

Commenter e-mail address.

$date : mixed = ''

GMT date of the new comment.

$avoid_die : mixed = false

Whether to return instead of calling wp_die().
