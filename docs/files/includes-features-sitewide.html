features-sitewide.php

Site-wide features

Two switches that mirror standalone JPKCom plugins hook for hook: xmlrpc (JPKCom Disable XML-RPC 1.0.10) and comments (JPKCom Disable Comments 1.0.11). Same hooks, priorities, accepted args and return values; only the callback names and the text domain differ, plus two documented exceptions: the XML-RPC fault text is an English literal, and the comment feed refusal stays a wp_die() 404 instead of going through jpkcom_harden_trim_force_404(). Both are global (no role exemption). The standalone plugins' findings up to their 1.0.10 were measured against WordPress 7.0.2; the Notes gate, the note-query pass-through and the comment count filter (Disable Comments 1.0.11) were read in the 7.1.3 source and not yet measured on a running site. The line references below are 7.1.3.

jpkcom_harden_trim_xmlrpc_refuse()

features-sitewide.php : 160

`init` priority 0: reject XML-RPC requests with a 403 and an XML-RPC fault.

jpkcom_harden_trim_xmlrpc_refuse() : void

The response is written here instead of being left to wp_die(). With XMLRPC_REQUEST defined, wp_die() dispatches to _xmlrpc_wp_die_handler(), which only emits anything when the global $wp_xmlrpc_server already exists (7.1.3 functions.php:4254), and xmlrpc.php creates that object after init (xmlrpc.php:82). That handler also never calls status_header(). Measured by the standalone plugin against 7.0.2: up to its 1.0.8 the endpoint answered HTTP 200 with an empty body.

Priority 0 puts it ahead of the text domain (1) and the updater (5), so a refused request does no further work.

jpkcom_harden_trim_comments_is_note_request()

features-sitewide.php : 298

Whether a REST request on the comment routes is a block-editor Notes request.

jpkcom_harden_trim_comments_is_note_request(WP_REST_Request $request) : bool

Notes (core since 6.9) are comments of type note, created and read through /wp/v2/comments. A request counts as a note request when

  • it targets the collection route and its type parameter is exactly note - the same strict comparison core's controller makes ('note' === $request['type']), for GET and POST alike;
  • it targets the item route /wp/v2/comments/<id> and that comment exists and is of type note (any method; core refuses to change a comment's type on update, 7.1.3 class-wp-rest-comments-controller.php:925).

The route is read from get_route() and matched the way core matches it (class-wp-rest-server.php:1172): case-insensitively, against the same [\d]+ item pattern, and with $ accepting a trailing newline as core's @^…$@i does. A trailing slash is tolerated as well. The ID is taken from the route because the URL parameters are not populated yet on rest_pre_dispatch: dispatch() applies the filter (:1079) before it matches the route (:1096), and a batch sub-request is passed with its URL parameters cleared (:1860-1866).

The controller itself does not use the ID in the route: it reads $request['id'] (class-wp-rest-comments-controller.php:435, :480, :873, :918, :1042, :1066), and get_param() prefers the JSON body, the form body and the query string to the URL parameters (class-wp-rest-request.php:362-384, :408-418). /wp/v2/comments/<note>?id=<n> would therefore load comment <n>. An item request with an id parameter is a note request only when that parameter is numeric and equal to the ID in the route. Read here, before routing, get_param( 'id' ) returns exactly the value core will prefer later, since the URL parameters are still empty.

Core's own permission checks still decide who may read or write notes.

The request about to be dispatched.

Whether a comment query asks for notes and nothing else.

Mirrors how WP_Comment_Query::get_comment_ids() reads the requested types (7.1.3 class-wp-comment-query.php:776-789): type and type__in are merged, and an empty string means "all types". `wp_loaded` callback: remove comment and trackback support from every post type.

Bound to wp_loaded, not admin_init: every post type is registered once init has completed (7.1.3 wp-settings.php:779 init, :801 wp_loaded), while admin_init and rest_api_init fire later. On admin_init (the standalone plugin up to 1.0.8) the removal never reached REST requests, so /wp/v2/posts kept reporting comment_status: open.

`comments_pre_query` callback: short-circuit every comment query except note-only ones.

jpkcom_harden_trim_comments_short_circuit_query(mixed $comment_data, WP_Comment_Query $query) : mixed

comments_array only covers the template path. The dashboard Activity widget queries comments straight through WP_Comment_Query (filter at 7.1.3 class-wp-comment-query.php:441), which is why the full moderation list still appeared there. dashboard_recent_comments has not been a widget since WordPress 3.8, so removing that meta box does nothing.

jpkcom_harden_trim_comments_block_feed()

features-sitewide.php : 529

`template_redirect` priority 0: refuse the comment feeds.

jpkcom_harden_trim_comments_block_feed() : void

Comment feeds are assembled by WP_Query directly through $wpdb (only the comment_feed_* filters apply), so they bypass comments_array and comments_pre_query: approved comments stayed readable at /comments/feed/ and <post>/feed/. /feed/ is unaffected, because is_comment_feed() is false there.

jpkcom_harden_trim_comments_rest_gate()

features-sitewide.php : 615

`rest_pre_dispatch` callback: close the REST comment routes to everything except block-editor Notes.

jpkcom_harden_trim_comments_rest_gate(mixed $result, mixed $server, mixed $request) : mixed

Up to Disable Comments 1.0.10 the /wp/v2/comments routes were removed on rest_endpoints. That also broke Notes, which core reads and writes through exactly those routes. The routes now stay registered, and this gate answers every request on them that is not a note request (see jpkcom_harden_trim_comments_is_note_request()) the way a missing route is answered: rest_no_route, core's own message (default text domain, so the translation is core's too) and status 404.

A request is on the comment routes when its route is /wp/v2/comments or lies below /wp/v2/comments/, compared case-insensitively as core does; ?rest_route= requests arrive with the same route. /wp/v2/commentsfoo and other namespaces are not touched.

PHP_INT_MAX, and a non-note request is answered even when an earlier filter already produced a result - that includes core's OPTIONS handler at priority 10 (7.1.3 rest-api.php:837), which would otherwise describe the route. For a note request the incoming value is returned unchanged.

The error is returned as a response, not as a WP_Error: in a batch request core passes a rest_pre_dispatch result straight on to rest_post_dispatch (class-wp-rest-server.php:1894), where rest_send_allow_header() calls get_matched_route() on it, which a WP_Error does not have. In a single request dispatch() returns the response as is - the same bytes as core's own missing-route answer.

Side effect: the route index at /wp-json/ lists the comment routes again; that is inherent to keeping them for Notes.
